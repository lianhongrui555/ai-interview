# Harness 理解（任务四）

> 题目任务四要求"参考 pi agent 的架构，搭建自己的 Harness"，并问"Harness 是什么呢？"
> 本文档给出我对 Harness 的理解。
> **本项目不实现 Harness 代码**，原因见文末"范围说明"。

## 一、Harness 是什么

一个**大模型本身只会"根据输入生成文本"**。它不能读写文件、不能执行命令、不能上网。

**Harness（字面意思是"马具/挽具"）就是套在模型外面的那一层框架，
让一个只会生成文本的模型，变成一个能真正做事的智能体（Agent）。**

类比：模型是发动机，Harness 是整台车的底盘、传动、方向盘和刹车。
发动机再强，没有这些也上不了路。

## 二、一个 Harness 的核心组成

| 组成部分 | 作用 |
|---|---|
| **主循环（Agent Loop）** | 反复执行：把上下文发给模型 → 拿到回复 → 判断是"最终答案"还是"要调用工具" → 执行工具 → 把结果塞回上下文 → 再来一轮 |
| **工具系统（Tool / Function Calling）** | 定义模型可以调用的能力：读文件、写文件、执行命令、搜索网页…… 并声明每个工具的名称、参数、用途 |
| **上下文管理（Context Management）** | 决定每一轮往模型里塞什么。对话变长后必须做压缩/裁剪，否则会超出模型的上下文窗口 |
| **系统提示词（System Prompt）** | 告诉模型它是谁、要遵守什么规则、怎么用工具、什么时候停下来 |
| **权限与确认机制** | 危险操作（删文件、执行命令）要不要先问人？这是安全边界 |
| **终止条件** | 什么时候算任务完成？防止无限循环烧钱 |

## 三、最小可运行的 Harness 长什么样（伪代码）

```
messages = [系统提示词, 用户任务]

while True:
    reply = 调用模型(messages, 可用工具列表)

    if reply 是普通文本:
        messages.append(reply)
        break                      # 任务结束

    if reply 要求调用工具:
        result = 执行工具(reply.工具名, reply.参数)
        messages.append(result)    # 把工具结果塞回上下文
        continue                   # 进入下一轮
```

**整个 Harness 的骨架就这么点东西。** 剩下的复杂度都在工程细节：
上下文怎么压缩、工具怎么设计得让模型会用、出错怎么重试、怎么防止它跑偏。

## 四、为什么说 Harness 才是"自己的华小牛"

题目原文说"既然大鲸鱼那么火，我们能不能有自己的华小牛"。

含义是：**模型能力大家都能买到或用开源，真正拉开差距的是 Harness 这一层。**

同样一个模型：
- 裸着用 → 就是个聊天框
- 配上好的 Harness → 能自己读论文、写代码、跑实验、检查结果、再迭代

**差距不在模型，在 Harness。**

## 五、我身边的实例

我现在日常使用的 AI 编程工具本身就是一种 Harness，
它的能力主要来自"工具调用 + 循环 + 上下文管理"这三件事，而不是某个更强的模型。
这让我对 Harness 的价值有非常直观的体会。

## 六、范围说明（为什么本项目不写 Harness 代码）

题目明确说："AI 会不断地把事情变繁琐，而你**需要为你的事情做减法**，
而不是不断的增加噪声。"

Harness 属于**进阶任务**，完整实现需要处理上下文压缩、工具协议、
权限控制、错误恢复等一系列工程问题，工作量远超剩余时间。

因此我的选择是：

- **理解层面**：用本文档讲清楚 Harness 的架构与关键问题
- **实现层面**：集中精力把任务一（模型部署 + API 接入应用）做完整、做干净
- **后续规划**：如果时间允许，会在此基础上实现一个最小 Harness
  （单工具 + 单循环），作为项目的进阶延伸

> 我的判断是：**把一件事做透，好过五件事都做一个开头。**
