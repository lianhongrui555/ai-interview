# 2026-10-05 YOLO 实时目标检测工程日志

> 说明：本日志根据 YOLO 项目的脚本、训练配置、验证结果和 Web 性能测试补记。

## 今日目标

- 在本地 GPU 环境完成 YOLO 模型训练与推理闭环。
- 将摄像头画面、后端推理和浏览器检测框显示打通。
- 对 V1 与 V2 的准确率、推理耗时和网页帧率进行量化比较。
- 保留可复现实验的脚本、配置、图表和最佳模型。

## 环境与总体思路

- 操作系统：Windows。
- GPU：NVIDIA RTX 5070 Ti，训练和推理均使用 `device=0`。
- 深度学习框架：PyTorch + Ultralytics YOLO。
- 后端：Flask。
- 前端：浏览器摄像头 + Canvas 检测框。
- 数据：Ultralytics COCO128 小型数据集，适合快速验证完整流程。

整体链路：

```text
COCO128 数据集
→ YOLO 预训练权重
→ GPU 训练
→ best.pt
→ Flask 推理服务
→ 浏览器摄像头上传图片
→ YOLO 返回检测框
→ Canvas 实时绘制
```

## V1：先跑通完整闭环

V1 使用 `YOLO11n`，目标是优先验证流程，而不是追求最高准确率。

训练参数：

- 模型：`yolo11n.pt`
- 数据：`coco128.yaml`
- 轮数：10
- 输入尺寸：640
- 批量大小：16
- GPU：设备 0
- 随机种子：42

Web 推理思路：

1. 浏览器通过 `getUserMedia` 获取摄像头画面。
2. JavaScript 把当前帧编码成 JPEG。
3. 通过 `POST /predict` 把图片发送给 Flask。
4. Flask 使用 OpenCV 解码图片。
5. YOLO 执行推理，返回边界框、类别和置信度。
6. 浏览器按图片尺寸缩放坐标，并用 Canvas 绘制检测框。

这个阶段成功证明了训练、模型加载、GPU 推理和前端显示可以连成一条完整链路。

## V2：在 V1 基础上做性能增强

V2 使用更大的 `YOLO11s`，并通过训练策略和推理尺寸测试提升效果与速度。

训练参数：

- 模型：`yolo11s.pt`
- 数据：`coco128.yaml`
- 轮数：50
- 训练尺寸：640
- 批量大小：8
- 自动混合精度：开启
- 余弦学习率：开启
- 最后 10 轮关闭 Mosaic
- 早停耐心值：15
- 随机种子：42

V2 没有直接假设“更大模型一定更慢”，而是继续测试不同推理尺寸：

- 640：准确率最高。
- 512：准确率略降，但批量推理和网页响应更快。
- 480：速度提升有限，准确率继续下降。

最终选择 `YOLO11s + 512` 作为网页版本，在准确率和实时性之间取得平衡。

## 最终数据

| 指标 | V1：YOLO11n / 640 | V2：YOLO11s / 512 |
|---|---:|---:|
| mAP50 | 0.742 | 0.904 |
| mAP50-95 | 0.567 | 0.769 |
| 网页客户端中位数 | 172.81 ms | 140.35 ms |
| 网页平均帧率 | 5.85 FPS | 7.30 FPS |
| 服务端推理中位数 | 104.43 ms | 94.94 ms |

V2 的 512 尺寸验证结果：

```text
Precision：0.9124
Recall：0.8385
mAP50：0.9038
mAP50-95：0.7687
```

## 工程中解决的问题

- 将 Ultralytics 和 Matplotlib 的配置目录固定到项目内部，避免系统目录权限问题。
- 将训练逻辑放入 `main()`，提高 Windows 多进程数据加载稳定性。
- 训练结果使用独立目录和 `exist_ok=False`，避免误覆盖历史实验。
- Web 服务启动时只加载一次模型，避免每个请求重复加载。
- 检测接口只返回结构化坐标，绘制工作放在浏览器 Canvas 中。
- 使用健康检查接口同时确认模型路径和 CUDA 状态。
- 对比网页性能时，先预热模型，再重复多轮测试，减少首次加载对结果的影响。

## 最终结论

这个项目完成了从数据、训练、模型评估到浏览器实时推理的端到端闭环。

V1 的价值是快速证明系统可以跑通；V2 的价值是通过模型升级、训练策略和输入尺寸实验，同时提高准确率和响应速度。这个过程体现了工程项目的正确推进方式：

```text
先跑通
→ 再测量
→ 找瓶颈
→ 做对照实验
→ 选择最适合目标的方案
```
